A two-day build log · November 22–24, 2026

Building a PlayStation in a Browser Tab

Two days, ninety-six commits, 407 tests, and one commercial racing game reaching its mission screen inside a web page. This is the complete story of psx-web: what we built, every bug that humbled us, why the GTE is the heart of the remaining work, and the architecture decisions that got us here.

Written from the source tree at apps/src/core/ · knowledge base in knowledge-base/ · 0 copied lines of emulator code

Chapter 00 · PrologueWhat a PlayStation Actually Is

Before anything else, it helps to say plainly what we were building. A PlayStation 1 is not one chip. It is a small 1994 computer with five subsystems that all have to lie about time in the same way at the same instant:

  • a CPU — a MIPS R3000A at ~33.87 MHz, with a quirk no modern chip has: every load takes effect one instruction late, and every branch executes the instruction after it before jumping;
  • a GTE — the Geometry Transformation Engine, coprocessor 2. A fixed-point vector math machine that turns 3D coordinates into screen coordinates and lit colors. The CPU has almost no useful floating point, so the GTE is the 3D pipeline;
  • a GPU — no 3D hardware at all. The GTE hands it flat 2D polygons and it rasterizes them, with affine texture warping and a 1024×512 halfword frame buffer called VRAM;
  • a CDROM controller, MDEC, SPU — the drive, the FMV/JPEG-style macroblock decoder, and the 24-voice sound chip;
  • and the glue: DMA (7 channels), an interrupt controller, three timers, two serial ports for pads and memory cards.

Our project constraint was unusual and, it turned out, clarifying: the browser is the engine. There is no server-side emulation, nothing to install. A visitor drops in their own BIOS dump or disc image and their own CPU does the work. That single constraint shaped everything — the language (TypeScript compiled by Bun, a React shell, a Web Worker for the emulation core), the memory discipline (preallocated typed arrays, no per-frame allocation), and the legal posture (we never ship a BIOS or a game).

The rule that disciplined the whole build

A task is complete only when its observable acceptance criteria are met. A loading bar, a title screen, and playable gameplay are separate milestones and must not be conflated.

Chapter 01 · The decision to startLearning From a Shipped Binary

We did not copy another emulator. We did read one, in the most literal sense: ePSXe 2.0.5 for Linux x64, a stripped ELF binary, taken apart in Ghidra. Two thousand five hundred and forty-nine functions recovered, mapped into knowledge-base/BINARY-RE-MAP.md. Not to lift code — the license forbids it and the architecture wouldn't match anyway — but to recover specifications: the shape of the CDROM command handlers (CdromIoIrqFunc1/2), the byte-exact semantics of LWL/LWR unaligned loads, the UNR division algorithm the GTE uses, the memory layout of a working emulator.

That last one matters more than it sounds. The reference binary holds about 20.7 MiB in fixed .bss globals — every piece of emulator state in flat, preallocated arrays. We mirrored that discipline: all emulation state lives in a handful of typed arrays allocated once, because a garbage collector pausing mid-frame is a dropped frame.

For hardware behavior beyond what the binary showed, the working references are the PSX-SPX documents (formerly no$psx), the public PS1 test ROMs, and hardware measurements published by other projects. Each module in our tree cites what it mirrors; every corner where our model is a guess rather than a verified fact carries an UNVERIFIED comment, so the next reader knows exactly where the map ends.

Provenance

Every subsystem in apps/src/core/ cites the binary function or spec section it was derived from. No emulator source was copied. Where hardware behavior was measured by other projects (for example, the MDEC's output rounding, measured on silicon), the measurement is cited, not reimplemented from their code.

Chapter 02 · What we builtThe Machine, Subsystem by Subsystem

Twenty-four source files under apps/src/core/, each held under 600 lines by rule, each owning one piece of the machine. This chapter is the tour.

CPU — cpu.ts, 514 lines

The MIPS R3000A interpreter: the full user ISA (SPECIAL/REGIMM, jumps and branches, ALU ops, loads and stores including the byte-exact LWL/LWR/SWL/SWR unaligned merge sequences taken from the reference binary), MULT/DIV with correct signed semantics, LL/SC (uniprocessor: always succeed), COP0 (MFC0/MTC0/RFE), COP2 dispatch into the GTE, LWC2/SWC2 GTE memory transfers, and the two signature R3000A hazards — the load delay slot and the branch delay slot — modeled explicitly rather than hidden. Exceptions route through a real CP0 path (CAUSE/EPC/SR doubling) with a BIOS-free fallback: if no handler sits at vector 0x80000080, the CPU emulates the BIOS default outcome and skips the faulting instruction.

GTE — gte.ts, 866 lines

Coprocessor 2, the fixed-point geometry machine. This grew from eight commands at the start of day two to all twenty-two commands in the psx-spx real-opcode table — every coordinate, general-purpose, color, depth-cue, average-Z, and interpolation command, including the two hardware bugs (MVMVA's broken FC translation vector, the RTPS IR3 flag quirk) that games quietly depend on. It deserves its own five chapters, and gets them below.

GPU — gpu.ts + gpu-raster.ts

1 MiB of VRAM as one Uint16Array (1024×512, 15-bit BGR555 with a mask bit at bit 15). The GP0 parser decodes polygon word counts from the command bits rather than a lookup of common cases: the 20h–3Fh polygon family (flat/gouraud × triangle/quad × untextured/textured), the 60h–7Fh rectangle family (variable/sizes 1×1, 8×8, 16×16), Fill-VRAM, CPU→VRAM image load, VRAM→CPU store, and the E1h–E5h draw-mode commands. GP1 handles display enable, DMA direction, display area, horizontal/vertical ranges, and mode — and the display rectangle is derived from those ranges the way the hardware does it (horizontal size rounded to four pixels, vertical exact), not from a fixed 640×480 assumption.

The rasterizer is software: a scanline integer DDA with all interpolation in 16.16 fixed point, closed spans (both boundary pixels drawn), quads decomposed into two triangles along the v1–v2 diagonal, 4-bit/8-bit CLUT and 15-bit direct textures, texture color modulation in the PS1's integer style, the four semi-transparency modes, the 4×4 dither table, and the drawing clip plus signed draw offsets. It renders into native VRAM — always — even in the 2×/4× internal-resolution mode, which scales only geometry and keeps VRAM semantics native.

CDROM — cdrom.ts, 560 lines

The drive controller as a state machine: a 16-deep parameter FIFO, a response FIFO with the hardware's wrap-and-replay read behavior, a one-deep queue for second responses delivered after the first is acknowledged, and the full command surface — Getstat, Setloc, Play, ReadN/ReadS, MotorOn, Stop, Pause, Init, Setfilter, Setmode, Getparam, GetlocL/P, GetTN/TD, SeekL/P, Test, GetID, Reset, ReadTOC — with the correct INT3-first / INT2-second / INT1-data / INT5-error rhythm and a latched error byte for INT5. Sector data is fed by host disc-image loaders; the controller itself knows nothing about files.

DMA — dma.ts, 172 lines

Seven channels with the real register file (MADR/BCR/CHCR triplets), DPCR enable nibbles, burst/block/linked-list sync modes, the OTC reverse-ordering-table channel, write-1-clear completion flags in DICR, and the derived master flag. Channel 2 drains GPU linked lists and raw block streams into the same GP0 sink; channel 3 is gated on the CDROM's data-request bit, because the drive will not be drained before it says data is ready.

SPU — spu.ts, spu-voice.ts, spu-audio.ts

24 voices, ADPCM block decode with the exponent/filter header, Gaussian pitch interpolation, the four-phase ADSR envelope, key-on/key-off, a 512 KiB sound RAM, an IRQ address comparator, and a WebAudio sink that receives bounded transferred buffers — never per-sample React state. Reverb, pitch modulation, and noise generators are documented skips.

MDEC — mdec.ts + mdec-bs.ts + mdec-tables.ts

The macroblock decoder behind full-motion video: run-level decode in both the fixed-length and Sony BS variable-length bitstream formats, an AAN fast-path IDCT for standard quant tables and a real-matrix general path for custom ones, YUV→RGB with the reference's exact constants (B uses 1.7754, not 1.772 — a genuine hardware quirk), and the measured output rounding: round half down, mask to signed 9 bits before saturating, so an overrun decodes black, not white.

Timers, pads, cards — rcnt.ts, joypad.ts, memory-card.ts

Three root counters with sysclk/pixel/hblank clock sources, sync modes, target reset, and one-shot/repeat IRQ behavior — including counter 2's synchronized stop modes. The SIO0 serial controller speaks the real pad protocol: 0x01 select, 0x42 read, the dual-shock config-mode command set (0x43 enter/exit, 0x44 mode/lock, 0x46/0x48/0x4C constants, 0x4D rumble mapping), analog axes, and rumble actuators. Memory cards are full 128 KiB images with the spec protocol (0x52 read / 0x53 ID / 0x57 write, XOR checksums, the "MC" filesystem header, a formatted-card factory), persisted in IndexedDB — never uploaded.

The shell — machine.ts, syscall.ts, loader/, state-*.ts, workers

machine.ts is the bus: the MMIO port map, the interrupt status/mask registers with write-zero-clear semantics, the per-slice scheduler (DMA → events → CDROM → SPU → timers → VBlank), and the BIOS-kernel interrupt delivery. syscall.ts is the HLE shield: A/B/C-call tables sufficient to boot real games without a BIOS. The loader family reads PS-X EXE, CUE/BIN, ISO, CHD v4/v5, PBP, and raw MDF. Save states are a versioned, schema-validated whole-machine format ("RPSX", version 6). The worker layer owns the Machine on a dedicated thread; the UI never touches emulator state directly. And an ePSXe-style React UI — menus, video/gamepad/memory-card dialogs cloned from a 598-widget GTK blueprint extracted out of the reference binary — wraps all of it.

Chapter 03 · Two days, 96 commitsThe Chronology

The git log reads like a compressed novel. Here it is with the connective tissue restored.

Phase 0–1 — something boots (Nov 22)

Checkpoint zero was a workspace and a knowledge base. Then the memory map — the full 4 GiB translation with its mirror regions, in one exhaustive test that walks all 65,536 pages. Then the CPU interpreter, the GTE first cut, the root counters, the PS-X EXE loader, and a React shell. The day's proof: a hand-assembled PS-X EXE, loaded through the real loader, executed by the real CPU, across the real bus, into the real GPU, putting a verified rgb(0,255,0) pixel on a canvas in a real browser. BIOS-free, because a PS-X EXE contains its own entry point and needs no retail boot ROM — only the handful of kernel calls a well-behaved program makes, which the HLE shield answers.

Phase 2–3 — the machine fills in (Nov 22, overnight)

The software rasterizer landed as a delegated slice (gpu-raster.ts, flat/gouraud, 4/8-bit CLUT + 15-bit textures, blends, dither) and was wired into the GP0 polygon path. Then the peripheral wave, each slice built by a separate agent and integrated behind a green suite: the CDROM controller, the SPU with its WebAudio sink, the MDEC, the seven-channel DMA, the disc loaders, and the full-machine snapshot/restore. Session notes tallied 237 tests green, strict TypeScript clean, CI gating every push.

Homebrew, then retail (Nov 23)

Nortis, a homebrew Tetris clone, became the first real game code to run: extracted from a MODE2/2352 image, booted BIOS-free, twelve million cycles executed. Its boot chain exercised everything at once — crt0 register init, the BLTZ preamble, A/B-call graphics and pad init, VBlank IRQs at ~60 Hz driving VSync waits. It stopped, honestly, at B_open: file I/O over the CDROM needs a BIOS filesystem layer, which became the next session's first ticket.

Then 3Xtreme, a commercial title, went through the browser. The commits between "boots 3Xtreme" and "reaches MISSION" are almost entirely fixes with regression tests attached — that's chapter 04. By the evening of Nov 23: FE.EXE → GAME.EXE, a real loading screen, the title screen, a live MISSION screen, an animated race, Start-button input accelerating and steering the car, pause and resume working. 407 tests, TypeScript clean, repeatable browser E2E covering rendering, run controls, fullscreen, audio unlock/mute/volume, persisted settings, and the native/2×/4× renderer switch.

Day three and the GTE gap (Nov 24)

The last commits are the interrupt-timing cluster (chapter 04) and — crucially — the first three GTE depth-cue and normal-color command commits. The rendering-fidelity work had begun. The RENDERING-BOTTLENECKS.md doc written at that milestone is the honest ledger: the game runs and animates, but scenes do not yet match a hardware reference frame, because the GTE and GPU command coverage is not yet complete. Chapters 07–12 are that ledger, expanded.

Milestone discipline

The README still says 3Xtreme is "not playable" even though a race runs. The distinction: input is verified only through Start-accelerate-steer for minutes at a time, and rendering fidelity is known-incomplete. The status field in the docs matches what was actually observed, not what we hoped.

Chapter 04 · Bugs that taught us the hardwareSeven Failures, Seven Lessons

The interesting bugs weren't typos. Each one was a place where our mental model of the console was wrong, and the game was right. Every fix below carries the narrowest regression test that fails without it — the standing rule of the project.

1. Branch delay slots, everywhere

The R3000A executes the instruction after every jump or branch before control transfers. We knew that. We got it wrong three separate ways anyway. The interpreter initially skipped the delay slot on JR/JALR. The dynarec broke load delay at block boundaries — a load whose value lands "next instruction" is a different thing when the next instruction is in a different compiled block. And most subtly: interrupts arrived between a branch and its delay slot, and the exception handler's save/restore didn't preserve the in-branch-delay state, so execution resumed on the wrong side of the branch. The fix introduced an explicit executingDelaySlot flag feeding CAUSE bit 31 and EPC adjustment, plus a slice-boundary rule in the run loop: if a slice ends between a branch and its slot, the slot executes interpreted so a linear compiled block cannot NOP-slide past a jump target.

The same class of bug showed up as an exception-vector NOP-slide: with no BIOS, the vector at 0x80000080 contained garbage that happened to decode as instructions returning past EPC — a wild resume that looked almost like progress. The final exception path checks the vector for a real handler and otherwise emulates the BIOS default outcome deterministically.

2. CDROM register banking and the data request

The CDROM controller exposes four register banks through two address bits, and every one of our early bugs lived in the gap between "what the spec says port 1 does" and "what port 1 does at index 3". Writes were routed through the register banks (da1af13) so that command writes only happen at index 0, interrupt-enable only at index 1, and the INT acknowledge write only at index 1 of port 3. Then the deeper one: the game enabled the data request (BFRD, port 3 bit 7) before the sector arrived, and we cleared the request state on every read boundary, so DMA channel 3 was gated off forever. The fix (2a5bf4b): the request bit may precede the sector; the data-request state persists until the sector is fully drained; and the DMA channel-transfer gate now polls the drive's actual request bit rather than an assumed readiness. Sector-size mode bits (2048 vs 2340-byte exposure), post-DMA sector advance, and repeated GPU/SPU DMA completion notifications filled out the cluster.

3. DICR completion flags and the interrupt that would not clear

DMA completion interrupts were being raised but never de-asserted, because we treated DICR like a status register instead of what it is: per-channel write-1-clear flags at bits 24–30, enables at 16–22, a master enable at bit 23, and a derived master flag at bit 31 that is computed from the others. The fix (61e8b1e, cc37ef4) implemented the real derivation — master flag = bus-error OR (master-enable AND any channel flag) — cleared it when acknowledgement drops the last flag, and cleared the CPU interrupt line (I_STAT bit 3) when the master flag falls. Edge-triggered delivery: the line fires only on the pending transition, exactly like the hardware.

4. COP2 control transfers: the GTE was half-blind

The game configured its camera by writing the rotation matrix, translation vector, projection distance H, and screen offsets — all control registers, written by CTC2. Our COP2 decode handled data-register transfers (MFC2/MTC2) but mapped control transfers onto data registers: every CTC2 wrote into the wrong file, so the GTE transformed every vertex with a stale identity matrix. The fix (39fc095) split the four transfer forms correctly (MFC2/CFC2/MTC2/CTC2, selecting the data or control file by rd), and a follow-up (0a42c7b) fixed LWC2/SWC2 masking register indices to 15 instead of 31 — a bug that silently aliased the upper half of both register files. After that fix, geometry on screen changed immediately: the first proof that the game had been transforming vertices with garbage.

5. SIO0 ACK timing: the pad that answered too early

The SIO0 protocol is a synchronous serial exchange where the peripheral pulls /ACK low after each byte to solicit the next. Our first implementation asserted ACK synchronously, inside the write — before the CPU had finished the transfer's own housekeeping — and held it forever. The pad and memory card state machines deadlocked mid-packet. Two commits (be599d6, 813a917) turned ACK into a timed signal: assert 100 cycles after the transferred byte, hold low 100 cycles, raise the ACK IRQ on the assertion edge only when the DSR-interrupt-enable bit allows, and let ERRRST and control-register resets cancel pending state. The joypad grew a tick() that the machine loop advances per slice.

6. RCNT2 free-run: the counter that stopped during interrupts

Root counter 2 gates itself off in "synchronized" modes — and our tick function treated every synchronized mode as stopped. Worse, the main loop ticked timers only per-slice, and slices were suspended entirely while an interrupt handler ran — so timer 2 froze inside handlers, and any game polling it for pacing stalled there too. Two fixes (ce203e9, b1c719f) narrowed both rules: only the genuinely stopped sync modes halt the counter (and only when the clock enable bit is set), and the handler-execution loop ticks RCNT, the joypad, and the VBlank accumulator one cycle at a time while guest code runs, so a handler that busy-waits on timer 2 sees it advance.

7. Interrupt chain dispatch: running what the game registered

The BIOS kernel API lets a game register interrupt handlers as chains: an ExCB structure per priority class holding a verifier, a FIRST function, and a SECOND function the FIRST may request by returning nonzero. We initially dispatched a single hard-coded handler. The fix (ce203e9, d19cc9e) walks the registered chains in priority order, runs FIRST, honors its nonzero return by running SECOND, and stops the whole walk when a handler exits via ReturnFromException — because that call semantically terminates the remainder of the dispatch, including lower-priority handlers and the custom exception hook. A later refinement (0a42c7b's sibling) chooses between the full chain walk and the legacy priority-0 handler based on which devices actually have pending work, so CD/DMA service is never starved behind pad-card polling — the device-priority dispatch rule that shows up again in chapter 16.

The meta-lesson

Every one of these seven was found by observing a real game doing a real thing, reproducing the failure deterministically, naming the first incorrect hardware observable — not the downstream symptom — and fixing that one thing with a test that fails without it. No game-specific bypasses, no forced PC jumps, no frame patches. The working rules in TODO.md forbid them, precisely because each would have "fixed" a symptom and rotted the emulator.

Chapter 05 · The CPU in detailInterpreting a 1994 Chip in 2026 JavaScript

The interpreter is one switch over the major opcode, executed per instruction, with state in flat typed arrays: 32 GPRs plus hardwired $zero, hi/lo, PC, nextPC, CP0, and a single load-delay slot. No object allocation per step — the low-RAM rule applies to the hottest loop in the program.

The two hazards, made explicit

Branch delay. A taken branch sets nextPc to the target and raises inBranchDelay; the next fetch executes whatever sits in the slot, and then control transfers. Link registers store pc+8 (past the slot), matching hardware. The dynarec compiles the slot into the same block as its branch and exits after it; the interpreter marks the slot with executingDelaySlot so exceptions record CAUSE.BD and back up EPC correctly.

Load delay. On the R3000A a load's value becomes visible to the instruction after next, not the next one. The interpreter models exactly one pending slot with overwrite semantics (two loads back-to-back: the second wins). One of our earliest formal bugs — Nortis crashing at a block boundary — was this delay being dropped when a load was the last instruction of a compiled block. The dynarec now either publishes the value at the top of the next emitted instruction or exports it as a pending slot that the host applies.

Unaligned access, the BIOS way

Unaligned LW/SW trap on real hardware, and the retail BIOS handler emulates the access byte-wise and returns — it does not halt the program. Without a BIOS our exception path would NOP-slide forever, so we perform the same byte-wise emulation inline, keeping LWL/LWR/SWL/SWR byte-exact from the reference binary's handlers (R_LWL @0x43ab20 and friends). CACHE is a no-op: the R3000A ignores it.

Exception entry

CAUSE gets the code, the pending-IRQ bit, and BD; EPC gets the faulting PC (minus 4 in a delay slot, plus 4 for reserved-instruction resume); SR doubles the privilege kernel/user bits. If a handler exists at 0x80000080 the CPU vectors there; otherwise it emulates the BIOS default and skips the instruction. This is also where the HLE syscall fast path hangs: a SYSCALL at the A/B/C trampoline addresses dispatches into syscall.ts directly, because the vector PCs themselves select the table.

Two tiers, one contract

The dynarec compiles basic blocks to WebAssembly and is strictly opt-in. The parity contract (chapter 18) is that enabling it changes performance only — identical programs produce identical interrupts, delay slots, exceptions, and memory traffic in both tiers.

Chapter 06 · The GPU and the software rasterizerOne Million Pixels of Integer Math

The PS1 GPU knows nothing about 3D. It consumes a command stream of 2D primitives — polygons, rectangles, lines — and fills spans. Everything "3D" about a PlayStation frame was computed before the GPU saw it, by the GTE. That division of labor is why the GTE chapter matters so much.

VRAM and the display path

VRAM is 1024×512 15-bit halfwords in one preallocated Uint16Array; bit 15 is the STP mask bit. The display area is any rectangle of VRAM: GP1(05h) picks the origin, GP1(06h/07h) give horizontal/vertical ranges, GP1(08h) the mode. Width derives from the horizontal range divided by the mode's cycles-per-pixel (10/8/7/5/4 for 256/320/368/512/640), rounded to four pixels; height is the exact scanline count. 24-bit mode unpacks VRAM's byte-packed triplets. Frame composition converts the active rectangle to RGBA8888 once per presented frame; scaling modes (2×/4× internal resolution) scale only subsequently-rendered geometry and are honest about it — fill/upload-only or 24-bit frames are nearest-native pixels, never advertised as enhanced.

GP0 decoding from the command bits

Polygon opcodes 20h–3Fh are a bit field: bit 3 picks tri/quad, bit 2 textured, bit 4 gouraud, bit 1 semi-transparent. Word counts decode arithmetically — vertex-0 color rides in the command word; gouraud appends n−1 color words after their position words; textured appends a texture word per vertex (CLUT base from vertex 0, texture page from vertex 1). Rectangles 60h–7Fh carry size in bits 3–4 (variable/1×1/8×8/16×16). Nothing is special-cased to a common path; the length comes from the bits.

The rasterizer contract

gpu-raster.ts is pure functions over VRAM, no imports, no DOM. Its documented conventions:

  • vertex coordinates sign-extend from 11 bits (X) and 9 bits (Y); pixels outside the drawing area are discarded; signed draw offsets apply after decoding;
  • a scanline integer DDA with all attribute interpolation in 16.16 fixed point — deterministic on float64 because every value stays an exact integer scaled by 2¹⁶;
  • spans are closed: both boundary pixels and the last scanline draw, so bottom edges include their vertices [UNVERIFIED: exact hardware edge-inclusion];
  • quads decompose along the v1–v2 diagonal, mirroring hardware [UNVERIFIED: diagonal choice];
  • texture modulation is PS1-style integer math: texel to 8-bit as (t<<3)|(t>>2), then (texel8 × col8) >> 7 clamped — col8 128 is unity;
  • semi-transparency has the four hardware modes (B+F/2, B+F, B−F, B+F/4), per 5-bit channel, applied when the primitive flag or a texel's STP bit is set;
  • the 4×4 dither table applies before the 5-bit output shift, keeping its native phase even at 4× geometry scale.

Texture windows and the set-mask-bit write filter are documented gaps — the first already pinned by the bottleneck ledger (chapter 07), the second optional for current titles.

Chapter 07 · Rendering bottlenecksThe Honest Ledger

At the MISSION milestone we wrote knowledge-base/RENDERING-BOTTLENECKS.md: the verified baseline (boot, input, loading, save states, 407 tests — all green) followed by the eight things standing between "animated race" and "frame-matches-hardware". The order is priority order. This chapter reproduces the reasoning; the deep dives that follow cover the largest item end to end.

The guiding sentence

WebGPU is a presentation technology, not an emulator-correctness shortcut. Fix GTE/GPU behavior first; consider WebGPU only after geometry and frames match hardware.

P1 — Incomplete GTE instruction set

At the time of the ledger, gte.ts handled only RTPS, NCLIP, MVMVA, NCDS, NCDT, OP, SQR, RTPT. Missing commands mean the game executes valid code that computes incomplete lighting, interpolation, and ordering-table output — scenes render wrong rather than failing. This is now mostly closed: chapters 09–12 describe the full command table we implemented against the psx-spx real-opcode list. What remains is register/timing semantics (below) and adversarial conformance beyond the current vectors.

P2 — GTE register semantics and timing

Correct math with incorrect delay still breaks geometry. The spec's load-delay rules matter: CFC2/MFC2 results reach the GPR one instruction later (Tekken 2 famously fills with broken geometry without this), and GTE memory transfers delay two instructions for command visibility. Our interpreter currently commits GTE register transfers synchronously — the arithmetic, saturation, and FLAG behavior are exact; the timing of register visibility is not modeled yet. That is the next GTE ticket, alongside the SXY/SZ/RGB FIFO order, IRGB/ORGB conversion timing, and adversarial overflow tests.

P3 — Incomplete GP0 coverage

Polygon and rectangle families decode correctly; the line family (commands 40h–5Fh) is absent entirely, and some rendering attributes (texture windows, mask-bit writes) are unimplemented. Menus and simple rectangles render while textured track geometry, HUD lines, and effects remain wrong. The fix is the same discipline as everywhere else: decode packet lengths from the command bits — already done for polygons and rects — and add command-by-command tests including textured lines and variable-size rectangles.

P4 — Texture pages, CLUTs, affine mapping

The renderer uses native VRAM textures with 4/8/15-bit paths, but texture-window wrapping and edge behavior are unverified against commercial scenes. A valid projection with wrong texture addressing looks materially different from a hardware frame even though the frame animates. Two things are settled policy: preserve PS1 affine mapping (no perspective-correct interpolation — the warping is the look), and compare composed-frame pixels against native VRAM for each texture path.

P5 — Rasterization, shading, edges

Edge inclusion, texture-window rounding, and quad decomposition are marked UNVERIFIED in the rasterizer header. Even with correct GTE math, edge errors, dither phase, semi-transparency order, and diagonal choice change visible output. The plan is deterministic pixel fixtures — triangles, quads, lines, clipping, texture windows — before touching fill behavior, plus hardware-measured references like Copetti's writeup for the inclusion rule.

P6 — DMA, IRQ, handler scheduling

Mostly closed by the day-two fixes (chapter 04): device-priority dispatch, DICR derivation, data-request gating. What remains is replacing the "one interrupt-bucket per slice" CDROM timing model and the ad hoc peripheral ticking with a deterministic event queue (TODO 4.2), so adjacent CD/DMA/VBlank completions order exactly as hardware would.

P7 — Presentation and frame pacing

Headless replay and a live browser can differ when RAF throttles or a tab pauses — host problems, not game-state differences. The fix already shipped: the cycle budget runs on elapsed console time, not display frames (chapter 15), and each input snapshot applies exactly once without resetting controller configuration (a real bug we hit: cfdc035). What remains is frame-hash comparison over minutes in a visible focused tab.

P8 — Audio and SPU/DMA timing

Chapter 08 · The GTE, explainedThe Coprocessor That Was the 3D

Stand where a 1994 game programmer stood. The R3000A has no floating-point unit. Not a slow one — none. Every multiply that matters is integer. If you want to place a textured, lit, perspective-correct-looking triangle on screen, you will do it in fixed point, and you will do it fast, because you need thousands of vertices per frame at 30 or 60 frames per second on a 33.87 MHz chip.

Sony's answer was to put the whole 3D pipeline in silicon next to the CPU: the Geometry Transformation Engine, coprocessor 2. It has no memory, no I/O ports, no DMA. The CPU feeds it registers, issues one opcode, waits a handful of cycles, and reads results back. In exchange it performs the vector/matrix heart of a 3D renderer — rotation, projection, lighting, depth cueing, clipping, ordering-table depth keys — in fixed point with hardware saturation, in 5 to 44 cycles.

What the CPU sees

The GTE is reached only through coprocessor opcodes:

mfc2 rt, rd     ; read GTE data register rd  (with a load delay!)
cfc2 rt, rd     ; read GTE control register rd
mtc2 rt, rd     ; write GTE data register rd
ctc2 rt, rd     ; write GTE control register rd
lwc2 rt, addr   ; load a GTE data register from memory
swc2 rt, addr   ; store a GTE data register to memory
cop2 0x0280030  ; execute RTPT — the command itself

That final form — COP2 with a 25-bit immediate — is the command. Everything else is plumbing. Two facts about the plumbing turned out to be the difference between "renders" and "renders correctly" for us: the control registers are where the camera lives (rotation matrix, translation, projection constants), and we initially didn't decode CTC2 at all (chapter 04, bug 4).

Why fixed point — and why 1.3.12

The GTE's native format is 1.3.12: one sign bit, three integer bits, twelve fraction bits. A value of 1.0 is stored as 4096 (0x1000). The rotation/light/color matrices hold 1.3.12 halfwords; the translation, background-color, and far-color vectors hold 32-bit 1.19.12 words; the accumulators are 32- and 44-bit integers that absorb the intermediate precision. The sf ("shift fraction") bit on each command says whether to divide results by 4096 — i.e. whether the inputs carried fraction bits or not.

Why not more integer bits? Because coordinates and normals are small, and the 1.3.12 range of ±8.0 covers every direction vector and every matrix element a game needs, with 12 bits of fraction precision — about 0.024% resolution — far beyond what a 1994 television could show. The accumulators exist precisely so the intermediate sums don't have to fit in 16 bits: MAC1..MAC3 are effectively 44-bit accumulators, and the FLAG register records when even those overflow.

Three of those are not registers in any comfortable sense: the SXY, SZ, and RGB files are FIFOs — every command that produces a screen coordinate pushes the pipeline down (SXY2←SXY1←SXY0, and so on for SZ and RGB). A game projecting a triangle runs RTPS three times and then reads all three SXY stages, or runs RTPT once and reads the same FIFO at once. NCLIP — the backface test — operates purely on the SXY FIFO. Get the push order wrong and polygons vanish or invert; get it right and the same FIFO serves projection, clipping, and depth-cue in sequence.

The classic per-vertex flow

; load vertex
mtc2  vx0, 0      ; VXY0 = (x,y)
mtc2  vz0, 1      ; VZ0  = z
; camera already loaded via ctc2: RT, TR, screen offsets, H
nop               ; (a real GTE needs this; see load-delay note in ch.12)
rtps  sf=1, lm=0  ; COP2 0x0180001 — project one vertex
; results: SXY2 = screen xy, SZ3 = depth, MAC1-3/IR1-3 = camera-space
;          IR0  = depth-cue factor, FLAG = saturation/error bits

Three vertices through that, then NCLIP to reject the backface, then AVSZ3 to make the ordering-table key, then a color command to light it, then the game writes a 9-word GP0 polygon packet whose screen coordinates came straight out of the SXY FIFO. That is a PlayStation frame's worth of geometry, thousands of times per second — and it is why the GTE, not the GPU, is where a PS1 emulator's 3D correctness lives.

Chapter 09 · GTE: the pipeline, cycle by cycleSaturation, Division, and FLAG

Every GTE command is the same small vocabulary applied in a different order: dot products against matrix rows, shifts, saturating stores, FIFO pushes, and one unusual division. Before the commands, the vocabulary.

MAC and IR — the two-stage accumulator

Every vector result passes through two stages. MAC1..3 hold the raw 44-bit sums; IR1..3 hold the 16-bit working values derived from them. Two decisions happen between the stages, and both are opcode bits:

  • sf (bit 19): store MAC = sum SAR (sf ? 12 : 0) — the shift that converts 1.3.12 products back to integers;
  • lm (bit 10): saturate IR at −8000h (lm=0, signed) or at 0 (lm=1, "limit negative"). Lighting code sets lm=1 because a negative light intensity must clamp to black, not wrap.

MAC overflow never saturates the stored MAC — the spec is explicit that MAC0..3 keep their raw (shifted) values — but sets FLAG bits 30–25. IR saturation clamps and sets bits 24–22. Both facts took careful reading: our first draft clamped MACs, which is exactly the bug class the FLAG contract exists to catch.

FLAG — the error ledger

FLAG (cnt31) is the GTE's contract with the game: bits 30–23 record MAC/IR/color overflow, bit 18 SZ saturation, bit 17 divide overflow, 16–15 MAC0 overflow, 14–13 screen-coordinate saturation, 12 IR0 saturation. Bit 31 — the one games actually test — is the OR of bits 30–23 and 18–13. Every command clears bits 30–12 at entry, and a game checks bit 31 after a projection to decide whether the vertex went off-screen and needs clipping. Our updateErrorBit() recomputes that OR after every command, and the test suite holds the invariant "bit 31 set iff any error bit set" over randomized inputs.

One deliberate asymmetry, straight from the spec: in RTPS/RTPT, the IR3 saturation flag (bit 22) always behaves as if lm=0 — it flags and tests acc SAR 12 even when sf=0 — while the stored IR3 value respects the real lm bound. Games depend on this; we reproduce it exactly, with a comment pointing at the spec note.

The division that isn't one

The perspective divide in RTPS needs H/SZ3 — a division. The GTE has no divider. Instead it uses a signed Newton–Raphson–style reciprocal built on a 257-entry table: normalize SZ3 into 8000h–FFFFh by a shared left shift, look up an approximate reciprocal, run two correction steps, and multiply. The psx-spx pseudocode (our unrDivide follows it verbatim, matching DuckStation's UNRDivide shape):

if (H < SZ3*2):           ; overflow path — result saturates to 1FFFFh
  z = count_leading_zeroes(SZ3); n = H << z; d = SZ3 << z   ; d in 8000..FFFF
  u = unr_table[(d - 7FC0h) >> 7] + 101h
  d = (2000080h - d*u) >> 8
  d = (80h + d*u) >> 8
  n = min(1FFFFh, (n*d + 8000h) >> 16)
else: n = 1FFFFh + FLAG.17/FLAG.31

The table itself is max(0, (40000h/(i+100h)+1)/2 − 101h) — generated once at module load, bit-equal to the hard-coded hardware table. The subtleties are everywhere: results of exactly 20000h saturate to 1FFFFh without raising the overflow flag; the 33-bit intermediate is emulated in float64 (which holds these integers exactly); SZ3=0 takes z=16. This function is pinned by its own test against hand-computed values, because every zoomed-in polygon on screen depends on it.

Screen coordinates and the depth-cue tail

After the divide, RTPS finishes with pure arithmetic: MAC0 = n·IR1 + OFX, screen X = MAC0 >> 16 saturated to −1024..+1023; same for Y with OFY. SX2/SY2 push the SXY FIFO, SZ3 pushes the SZ FIFO. On the last vertex of a primitive (RTPS, or the third vertex of RTPT), the depth-cue tail computes MAC0 = n·DQA + DQB and IR0 = MAC0 >> 12 clamped to 0..4096 — the fog interpolation factor the color commands will use.

Command timing, and why we model it loosely

Hardware cycle costs are known exactly — RTPS 15 cycles, RTPT 23, NCDT 44, the little commands 5–8 — and the CPU stalls until a command finishes, so net cost is knowable. Our model executes commands atomically and doesn't charge their cycle counts to the interpreter's counter; timing fidelity here is an open item tied to the wider event-queue work (chapter 07, P6). The stall behavior itself is free: an atomic execution is indistinguishable from a stall at our slice granularity.

The psx-spx real-opcode table (bits 0–5 of the command word) lists every command the hardware executes. Ours now covers the table: every coordinate, general-purpose, color, depth-cue, and interpolation command, plus the two hardware quirks. The families tell the story better than a flat list.

RTPS is the pipeline of chapter 09. RTPT is documented as exactly three RTPS evaluations over V0/V1/V2 — our implementation calls the same core three times and the 10k-vector property test asserts full FIFO equality with three manual RTPS runs. MVMVA deserves its own paragraph because it is the GTE's instruction set within the instruction set. Its opcode bits select: which matrix (17–18: RT, LLM, LCM, or "garbage"), which vector (15–16: V0/V1/V2 or IR), which translation to add (13–14: TR, BK, FC, none), plus sf/lm. Every lighting command is essentially an MVMVA with fixed selectors plus a tail. Games use raw MVMVA for their own fixed-point linear algebra — skeletal skinning, wave functions, custom shading. The garbage-matrix selector (mx=3) isn't a joke: the hardware really multiplies by a nonsense matrix built from −R·10h, +R·10h, IR0 and stray RT elements, and our implementation reproduces it, because demos use it. And the FC translation selector (cv=2) hits a genuine hardware bug — the FC term is computed, then dropped: each row ends up with only the first matrix element's contribution. DuckStation calls this MulMatVecBuggy; we mirror it row-for-row, because games that hit the buggy path were written against the buggy hardware.

OP — the cross product — reads its "second vector" from the rotation matrix's diagonal (RT11, RT22, RT33 misused as D1/D2/D3), a hardware quirk our implementation documents rather than "fixes". SQR squares IR with no lm effect (results are never negative). LZCS/LZCR implement the count-leading-bits unit games use for fast normalization.

Every one of these bottoms out in the same hardware two-step, documented in the spec as "Details on MAC+(FC−MAC)*IR0": step 1 computes and stores (FC<<12 − MAC) SAR (sf·12) into IR with lm=0-style saturation, step 2 adds IR0·IR back and re-saturates with the real lm. Our interpolateColor() implements exactly that two-step form — an earlier one-step version produced off-by-small-amounts fog colors that the golden vectors caught.

The opcode-numbering trap

One of the strangest corners: PS1 assemblers historically wrote GTE commands with fake opcode numbers in bits 20–24 that the hardware ignores entirely — only bits 0–5 matter. The two numbering schemes disagree (fake 06h is DCPL, real 06h is NCLIP; fake 17h is OP, real 17h doesn't exist). Our first ticket specified commands by fake numbers and produced a dispatch table that collided with different real commands. The fix was to make the real-opcode table authoritative — execute() switches on bits 0–5 only — with a comment documenting the collision so the next reader doesn't re-derive it the hard way.

Chapter 11 · GTE: what breaks when it's wrongSymptom Atlas

The reason the GTE got five chapters is that its failure modes are diagnostic. When something is missing here, the screen doesn't go black — it tells you precisely which link in the pipeline is broken. This chapter is the atlas we used while the commands were landing.

Missing projection commands → static or exploded geometry

Without RTPS/RTPT the game cannot turn object-space vertices into screen coordinates. Emulators that stub these see either nothing (vertices stay zero), frozen geometry (stale SXY FIFO), or "exploded" scenes (unscaled camera-space coordinates interpreted as screen space). Every world-space thing — the track, the car, opponents — moves through RTPS thousands of times per frame.

Missing color commands → flat, black, or unlit scenes

NCS/NCT/NCCS/NCCT/NCDS/NCDT/CC/CDP produce the per-vertex colors the GPU interpolates. Miss the LLM stage and lighting goes flat; miss the LCM stage and surfaces take the background color; miss the depth-cue tail and fog polygons turn solid far-color. A scene that renders with correct geometry but wrong shading is a color-family gap, nearly always NCDT or its tails — which is exactly what 3Xtreme showed before the last three GTE commits.

Missing interpolation commands → broken fades, fog, and UI blends

DPCS/DPCT/INTPL/DCPL/GPF/GPL drive screen fades, distance fog, and the smooth color ramps of menus and damage flashes. Games also use GPF/GPL as general fixed-point lerp units for their own animation. Missing them shows as pops instead of fades, or as animations that snap between keyframes.

Missing NCLIP/AVSZ → vanished or wrongly-ordered polygons

NCLIP is the backface test; without it (or with a sign error) either the front or the back half of every model disappears. AVSZ3/4 produce OTZ, the index into the game's ordering table; without a correct OTZ, transparent and overlapping polygons sort wrongly — water behind terrain, HUD behind sky. The GPU draws in FIFO order; the game's entire depth strategy is sorting into that table with OTZ.

Wrong saturation/FLAG → geometry that's almost right

The nastiest class. If MAC values saturate when they shouldn't (or IR clamps to the wrong lm bound), most vertices are fine and the outliers explode: distant geometry shreds into streaks, zoomed-in walls tear, fog flickers. If bit 31 isn't the OR of the right subsets, the game's clipping logic misfires and culls visible geometry. This is why the test suite holds the FLAG invariants over randomized inputs rather than a few golden values.

Wrong divide → the zoom test

The UNR division is deliberately inexact — it's a fast reciprocal, and real hardware has its specific error pattern. A perfect H/SZ3 produces subtly different screen coordinates that accumulate over animation into visible jitter; the notorious artifact shows when the camera closes in and SZ3 gets small, where the H < SZ3·2 overflow path saturates coordinates. Our implementation reproduces the table and the min() saturation rule rather than "improving" the math — the hardware's exact error is part of the spec.

Missing timing → the Tekken-2 class of bug

CFC2/MFC2 results arrive one instruction late on hardware; commands reading registers take 5–44 cycles during which the CPU stalls rather than reads stale data. Games written against those delays — Tekken 2 is the canonical case — fill with broken geometry when an emulator commits transfers synchronously. This is the one GTE area we have not finished (P2 in the ledger): our arithmetic and FIFO order are exact, register visibility is instantaneous. It's next on the GTE list.

Why "the game still runs"

The CPU can execute valid opcodes the GTE ignores — our unknown-opcode path leaves FLAG cleared and returns, and the game code proceeds. That's precisely why incomplete GTE coverage is insidious: no crash, no exception, just a scene that slowly reveals every missing link. The FLAG contract is the only error channel, and only a frame-by-frame comparison against a hardware reference surfaces the gap.

Chapter 13 · Sound, disc, and the frozen decadeThe Subsystems Behind the Game

Three subsystems rarely appear in screenshots but decide whether a game runs: the disc chain, the sound chip, and the video decoder.

The disc chain

A game never reads "a file"; it reads sectors. The chain: an image format parser (CUE/BIN with multi-file INDEX anchoring and sync-pattern detection for raw ISO; CHD v4/v5 with its hunk map, zlib raw-DEFLATE hunks, mini self-referencing hunks, and version-dependent flat/compressed layouts; PBP; raw MDF) produces 2352-byte sectors; an ISO-9660 reader walks the directory tree over those sectors; the CDROM controller latches a sector into its buffer; and DMA channel 3 drains it into RAM — but only while the drive's data-request bit says the buffer is valid. Every layer is separately tested (34 loader tests, 23 controller tests, cross-module DMA tests), because each one has its own way of being subtly wrong.

The SPU

24 voices, each a small DSP loop: fetch an ADPCM block from sound RAM, decode with the block header's shift and filter coefficients, interpolate through the Gaussian table at the voice's pitch, shape with the four-phase ADSR envelope, mix. The 512 KiB sound RAM is another preallocated array; the data port and transfer-address register handle DMA-style uploads; an IRQ address comparator fires the SPU interrupt line for streaming games. The WebAudio sink receives fixed-size transferred buffers — bounded, never per-sample callbacks into the UI. Reverb, pitch modulation, and noise are documented skips with UNVERIFIED notes, sequenced behind the ledger's P8.

The MDEC

Full-motion video on a PS1 is a clever fraud: a JPEG-style macroblock decoder in silicon, fed by DMA channel 0, outputting raw 15-bit or 24-bit frames through channel 1 at the rate the streaming code drives. Our MDEC implements both input bitstreams (fixed-length run-level and the Sony BS variable-length front end), the AAN fast IDCT for standard quant tables and the real-matrix general path for custom ones, the YCbCr→RGB conversion with the reference constants, and the measured precision model — round-half-down output, signed-9-bit mask before saturation, so overruns decode black. STP passes through to the frame's mask bit. 41 tests including golden vectors and a full DMA decode cycle.

Chapter 14 · Why HLE instead of a BIOSBooting Without the ROM

The retail BIOS is a 512 KiB copyrighted ROM. We can't ship it; users may supply their own dump, and the loader accepts one (validated to exactly 512 KiB, mapped at 0xBFC00000, CPU reset into it — the real-BIOS path is real). But most of what games actually need from the BIOS is not code — it's answers. So we built both paths, and the HLE path is the default.

The trampoline trick

BIOS services are called through fixed vectors at 0xA0 (file functions), 0xB0 (system functions), and 0xC0 (I/O functions). The game sets $t1 to the function number and jumps; the vector is expected to dispatch. Our HLE installs two-instruction trampolines there — SYSCALL; JR $ra — and the CPU's syscall fast path recognizes vector PCs and dispatches into syscall.ts with the table encoded by which vector was hit. The game believes it called the BIOS; it called us.

What the shield answers

  • Memory: malloc/free over a bounded kernel arena, InitHeap;
  • Timers: the full InitTimer/GetTimerStatus/EnableTimerIRQ/DisableTimerIRQ/RestartTimer set, backed by the real RCNT module;
  • Events: OpenEvent/CloseEvent/EnableEvent/DisableEvent/TestEvent/WaitEvent/DeliverEvent — a real event table whose callbacks fire when devices signal (CDROM INT classes, VBlank, DMA completion), including the mode distinction between callback events and status events;
  • Interrupt chains: SetInterruptHandler/ReturnFromException/SetDefaultExitFromException/SetCustomExitFromException — the machinery from bug 7;
  • Pads: PadInit/PadGetButtons writing live button state, active-low, pad2 high / pad1 low;
  • Graphics: GPU_cw pushing words into the real GP0 parser; LoadAndExecute reading an ISO file and launching it; FlushCache; A-table SaveState/RestoreState register save/restore; ChangeClearPAD/ChangeClearRCnt.

The rule from the TODO governs the ethics of this layer: HLE failures are explicit; a stub never returns fake success solely to advance a game. FileOpen, for instance, reports exactly what it is — unimplemented — rather than handing back a handle to nothing. That honesty is why the Nortis B_open stall was a known limit rather than a mystery: the game asked for a file through BIOS FS emulation we hadn't built, the HLE said so, and the ticket was written.

Boot, end to end

loadExe installs the trampolines, sets the crt0 register contract the real BIOS establishes ($gp from the header, $sp/$s8, $ra to an exit-loop stub, $r5 = −1 so the crt0 BLTZ preamble takes the save path), fills the unwritten stack region with the exit-loop address so never-initialized link slots return to a spin instead of crashing, enables the display the way the BIOS handoff does, and resets the CPU to the EXE's entry PC. From there, the game is on its own — which is the point.

Chapter 15 · Workers and the cycle budgetKeeping the Browser Honest

A browser tab is a hostile runtime for an emulator: the scheduler throttles timers, requestAnimationFrame pauses in background tabs, garbage collection stops the world, and the main thread is shared with every DOM layout. The architecture answers all four.

The worker owns the machine

The entire Machine lives on a dedicated Web Worker. The UI sends a small, strictly-validated protocol — boot, run, pause, reset, input, set-renderer, save/load state, memory-card operations, frame requests — and gets back responses with transferred buffers: frames as ArrayBuffer RGBA, audio as left/right float pairs, card images, state blobs. Zero-copy transfers, bounded queues, request IDs with timeout detection, and a restart path if the worker dies. React never holds emulator state; it subscribes to a tiny store of UI facts (lifecycle, FPS, settings) and paints canvas from the transferred frame buffers. This mirrors the reference emulator's own GPU main/soft-mt thread split — the same shape, in browser primitives.

The cycle budget

The host never asks "run one frame per RAF". It accumulates elapsed wall time and converts it to console cycles at the fixed rate of 33,868.8 cycles per millisecond — the PS1's actual clock — then requests that many 20,000-cycle slices (at most 170 per run request, at most 3,386,880 cycles of catch-up after a stall). The consequences are deliberate:

  • a 144 Hz display runs the same console speed as a 60 Hz one — game speed is decoupled from refresh;
  • a throttled or hidden tab catches up by a bounded 100 ms and never fast-forwards an hour of backlog;
  • inside each slice the ordering is fixed: pending IRQ delivery check → CPU run → joypad tick → handler dispatch → DMA → event callbacks → CDROM pump/exec → SPU mix → timers → VBlank accumulator. Deterministic across runs, which is what makes save states and checkpoint comparison possible at all.

Input and audio, the same discipline

Input arrives as a coalesced, revision-numbered snapshot; the worker applies each snapshot exactly once and acknowledges by revision, and applying it never resets peripheral configuration (that bug — cfdc035 — taught us the difference between "update button state" and "re-initialize the pad"). Audio flows through a preallocated ring sized to the maximum run batch; overflow is counted and reported as droppedFrames rather than allowed to grow the queue; autoplay unlock is an explicit user gesture with clear muted/running state.

Chapter 16 · Devices, priorities, interruptsThe Nervous System

The interrupt system is where correctness bugs disguise themselves as timing bugs. One register pair governs everything: I_STAT (status, write-zero-clear) and I_MASK, bit per device — VBlank, GPU, CDROM, DMA, timers 0–2, SIO0, SPU — and an interrupt reaches the CPU only when status AND mask are nonzero and the CP0 status register has interrupts enabled.

Device-priority dispatch

The day-two discovery: dispatching interrupts as a flat queue let pad-and-memory-card event service run ahead of CDROM and DMA completions, and the game's asset loads starved — repeated CD retries, truncated handler runs. The rule that fixed it (ce203e9, refined through 61e8b1e and the pad-dirty refinement): when VBlank and a data device (CDROM/DMA) are both pending, the device path wins the dispatch choice; the full kernel chain walk runs only when pad-card work actually changed input or no device is pending. Device IRQ delivery stays ahead of lower-priority PadCard work, exactly as the ledger's P6 prescribes.

Lines from real state, not frame counters

Every interrupt line asserts from its device's completion condition: DMA's from the derived DICR master flag (chapter 04, bug 3), CDROM's from response/interrupt-flag registers per INT class, timers from RCNT target/overflow with one-shot vs repeat behavior, SIO0's ACK IRQ from the timed assertion edge. Nothing keys off "a frame happened". The VBlank accumulator is the one sanctioned abstraction — cycles/33.8688ms, a physical fact — and even it ticks inside handler execution so a handler that waits on the next frame doesn't deadlock.

Handler state, all of it

Entering a kernel handler snapshots registers, CP0, PC/nextPC, hi/lo, the branch-delay flag, and the pending load delay slot — committing the interrupted load's value for the handler without consuming it in the caller (an interrupt logically arrives after the load completed). Each nesting level gets its own stack region so nested handlers can't corrupt each other's frames, a bug we hit twice (db1788f, f9df471) before making depth part of the stack address. Exit honors ReturnFromException semantics: the custom-exit hook can restore a full register image the game saved, and a handler exiting that way skips the rest of the dispatch chain. Handlers are bounded at a million steps with diagnostics recording any truncation — a bounded lie, reported rather than hidden.

Why this matters beyond stability

Handler timing changes when input and CD DMA complete — which changes when the game's callbacks run — which changes what the player sees. Frame-accurate behavior isn't a polish item; it falls out of getting the nervous system right.

Chapter 17 · Save statesFreezing a Machine Mid-Thought

A save state is the whole machine, serialized: RAM (2 MiB), the scratchpad, the parallel port expansion, BIOS, VRAM (1 MiB of halfwords), every CPU register including the pending load-delay slot and branch-delay flag, all 64 GTE registers, the GPU's parser mid-command state (accumulated packet words and counters — because a state taken mid-polygon must resume mid-polygon), the SPU's 24 voices with decode buffers and envelope phases and the entire 512 KiB sound RAM, the CDROM's FIFOs and drive state, all 21 DMA registers with DPCR/DICR, the timers, the MDEC's block pipeline, the joypad and card protocol state, the HLE kernel's event table and interrupt chains, and the interrupt status/mask pair.

The format is versioned ("RPSX", currently version 6) with a declarative schema: typed arrays, bounded arrays, enums, nested objects. Encoding and decoding are schema-driven and the decoder validates the entire input before touching live state — a corrupt or wrong-version blob is rejected without modifying the running machine, with slot metadata, timestamps, and game identity stored alongside in IndexedDB.

The property that made this trustworthy: save → load → run produces identical traces and frames, tested as replay equivalence on every stateful module as it landed. The standing rule from the plan — "serialize pending queues and delayed operations, not only visible registers" — is exactly what the load-delay slot, the CDROM response queue, and the GPU's half-decoded packet represent.

Chapter 18 · The dynarec detourCompiling MIPS Into WebAssembly

An interpreter is honest and slow: one decoded switch per instruction, forever. The dynarec tier compiles basic blocks — straight-line runs ending at a branch (including its delay slot), a store that might alias code, or a 64-instruction cap — into WebAssembly functions. A hand-rolled binary emitter writes the WASM module bytes directly: no toolchain, no runtime codegen beyond WebAssembly.instantiate.

The design constraints were semantic, not speed: parity with the interpreter on everything. The emitted code mirrors the CPU state image at fixed word offsets in an imported linear memory, executes the block in WASM locals ($r0 constant zero), and syncs pc/nextPc/cycles back through one epilogue both taken and not-taken paths converge on. Loads and stores go through imported host callbacks so the host Memory and MMIO stay authoritative; PS1's load delay reproduces exactly (publish at the top of the next emitted instruction, or export a pending slot if the load was the block's last); the branch delay slot compiles into the same block, and the block exits after it.

Invalidation is the dynarec's eternal enemy: every bus-master RAM write (CPU stores, DMA writes) invalidates overlapping blocks; wholesale memory or saved-state replacement flushes everything. Handlers still run interpreted on purpose — their per-instruction RCNT ticking and GTE/HLE/CP0 behavior must not be coarsened to block-granular timing. And a slice that ends between a branch and its delay slot executes the slot interpreted, so a linear block can never NOP-slide past a jump target.

The verification is the acceptance criteria from the plan, unchanged: parity suites and deterministic boot checkpoints match; enabling it changes performance only, never visible behavior or save-state compatibility. It remains opt-in.

Chapter 19 · Where this goes nextThe Road to First Release

The TODO file is a phase plan with acceptance criteria, and the release gate is unusually concrete: 3Xtreme reaches its title screen and enters a real race through normal input; gameplay responds for several minutes with stable graphics and no invalid execution; display modes work at native resolution; audio works or is labeled unsupported; save-state and memory-card claims match implemented behavior; full gates green; no copyrighted assets. Only then tag a release.

The work between here and there, in the plan's own order:

  1. Finish CDROM streaming semantics (1.3): ReadN/ReadS/Pause/Seek/error transitions, INT1/2/3/5 sequencing, XA filtering, multi-sector and interrupted-read tests — repeated asset loads without stale data or duplicate completions.
  2. Event/IRQ/DMA/timer interaction (1.4) and the system-wide cycle scheduler (4.2): a deterministic event queue replacing per-slice peripheral ticking, validated for long-run drift and pause/resume.
  3. GPU completeness (3.4): audit all GP0/GP1 families, add the line commands, texture windows, mask bits; golden images for observed corruption before changing raster behavior.
  4. GTE timing (ledger P2): load-delay visibility, cycle charges, IRGB/ORGB — with the public test programs as the acceptance harness.
  5. Audio accuracy (4.1): voice timing, SPU DMA events, underrun recovery during real gameplay.
  6. Analog + rumble completion (2.3), BIOS-HLE audit vs real-BIOS parity (5.3), hot-path allocation elimination (7.2), and the legal homebrew compatibility suite (8.1) so CI never needs a commercial disc.

Then documentation that matches observed behavior (8.3), and the release itself (8.4). The broader ambitions — higher compatibility, a WebGPU presentation backend, performance headroom — wait behind the gate, deliberately.

What two days bought

A from-scratch emulator that boots a commercial PlayStation game to an animated, steerable race in a browser tab — with every subsystem tested against independent models, every limitation written down, and no line of anyone else's emulator in the tree. The remaining distance is measured in hardware behavior we can name precisely. That's what honest looks like.
